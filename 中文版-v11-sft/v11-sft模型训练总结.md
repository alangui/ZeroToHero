# 中文 GPT 模型训练总结 v11-sft（基座 v10 → 对话助手）

- 日期：2026-09-19
- 硬件：RTX 4060 Laptop（8GB 显存）
- 代码：`sft_zh_v11.py` + `prepare_sft_data.py` + `download_sft_data.py`
- 定位：**v10 基座 + 指令微调（SFT）→ 可对话的 GPT 助手。相对 v10 的唯一变量 = +SFT**
- 基座：`../中文版-v10-gpu/model_best_zh_v10.pt`（234.5M，永久基准 3.1819）

## 一、训练配置与数据集

| 项目 | v10 预训练 | v11 SFT |
| --- | --- | --- |
| 任务 | 基座语言建模 | 指令对话（回答部分计 loss） |
| 数据 | wiki 0.3b（2.0 亿 token） | alpaca-gpt4-zh + Belle 混合指令 40275 条（464 万 token，回答占 57.4%） |
| 词表 | 16000 | **16003**（扩 USER/ASSISTANT/EOT 三行，N(0,0.02) 初始化） |
| 样本形态 | 1024-token chunk 流 | 变长样本（均值 115，最长 256）+ padding + loss mask |
| LR | 3e-4 → 3e-5 | **2e-5 → 1e-6**（warmup 30 步） |
| batch | 32 | 16 |
| dropout | 0.2 | 0.1 |
| 梯度检查点 | 开 | 开（首跑关闭 OOM，详见 2.5 节教训） |
| 步数 / epoch | 32000 / 1.31 | **2000 / 0.79** |
| best 保存门槛 | iter > 20000 | 无门槛 |

数据配方：`download_sft_data.py` 合并 alpaca-gpt4-zh（47925 条）+ Belle（48958 条新增），
MD5 去重后随机采样 5 万，`prepare_sft_data.py` tokenize 后丢弃超 256 token 的 9725 条
（丢弃率 19.5%，Belle 回答短，显著低于 alpaca 单用的 33%）。

### 2.2 训练开销

| 指标 | 值 |
| --- | --- |
| 总耗时 | **89.5 分钟**（单步 2.69 秒） |
| 显存峰值 | 未记录（OOM 修复后无压力运行，估 6.5GB 量级） |

单步 2.69 秒约为 v10（1.71 秒）的 1.6 倍，但 token 吞吐只有 v10 的一半左右——
batch 小 + 序列短，GPU 吃不满，检查点重算的固定开销占比被放大。SFT 不需要拼吞吐，可接受。

### 2.3 永久基准集遗忘检查 ⭐

| 模型 | 基准集 val loss | 相对 v10 |
| --- | --- | --- |
| v10（基座） | 3.1819 | 基准 |
| **v11-sft** | **3.3877 ± 0.1991** | **+0.206** |

判读：落在 "+0.1 正常 / +0.3 回炉" 区间的中间，**轻度遗忘，可接受**。原因符合预期——
SFT 把权重拉向对话分布，wiki 纯文本上的读数变差是必然的；`-100` mask 只影响 loss 口径，
不影响模型结构上对 wiki token 的建模能力。若未来要"助手能力和基座能力兼得"，
方向是更小 LR / 更少步数 / LoRA 只训低秩增量，而不是全参 SFT。

### 2.4 关键结论

1. **SFT 第一步就成功**：EOT 收口、多轮格式、temperature/top-k 采样开箱即用（冒烟测试 ①②③④ 全过），loss 曲线单调健康，无灾难性遗忘
2. **格式学习快得惊人**：200 步（约 6 分钟）内 val 即跌穿基座 wiki loss——对话格式对基座是"举手之劳"，真正消耗训练量的是回答风格的打磨
3. **best 出现在 1600/2000 步**（LR 已衰减至 2.87e-6）：后期 val 仅微幅回升，未见明显过拟合，0.79 epoch 的预算合理
4. **词表扩维手术验证通过**：三个新符号从 N(0,0.02) 起步到正常参与训练，全程无 size mismatch / 结构漂移

### 2.5 教训存档：OOM 与检查点

首跑（2026-09-19 15:19）在第一步训练即 OOM（8.58GB 顶满，`free: 0` 碎片死法）。
根因：搭建脚本时判断"SFT 样本短、可关梯度检查点省 30% 速度"，账面上 batch 16 × 255
约 8.3GB，贴死上限。**同款 8GB 卡的纪律：凡 234.5M 全参训练，检查点默认开**。
修复后（`52fef27`）batch 16 原样保留，仅重开检查点，89.5 分钟跑完——用 30% 速度换显存
安全是正确交换，"短跑不用检查点"的想法错在把 v10 的峰值数字当成了常态余量。

## 三、优化建议

### 3.1 欠账（按优先级）

| 欠账 | 说明 |
| --- | --- |
| **chat() 盲测** | 训练后未留对话 transcript：需验证多轮上下文记忆、EOT 收口、长回答不被 256 截断。v11 的验收 ① 只做了训练前的管线冒烟 |
| 生成质量验收（v8 欠到现在） | 用 best 模型 temperature 0.8/top-k 50 生成，与 v10 裸生成盲测对比 |
| Belle 拒答样本过滤 | Belle 混有"我很抱歉无法回答"式输出（samples.txt 样本 0 即典型），若盲测发现助手爱道歉，在 `download_sft_data.py` 的 `normalize()` 加规则过滤 |

### 3.2 下版本方向（按优先级）

| 方向 | 理由 | 预测 |
| --- | --- | --- |
| **部署闭环** | SFT 的终点是可用的助手：FastAPI/Gradio 包一层流式接口（234M fp16 ≈ 470MB，Mac MPS 可跑） | 工程项，无数值预测 |
| block_size 256 → 512 | 长回答/多轮被截断会学到"说半句话"；扩 position_embd 后微调是标准做法 | 长对话体验质变 |
| 数据配方 v2 | Belle 清洗（拒答/低质）+ 更多多轮数据（Firefly） | val -0.05~-0.15 |
| 保基座能力的 SFT | LoRA 或更低 LR 更短训，把遗忘从 +0.206 压到 +0.1 内 | 基准 +0.1 内 |
